# PT-03 — Frontend: pantallas Recuperar contraseña y Restablecer contraseña

_HU-002: Recuperar contraseña olvidada por correo electrónico_

Pantallas standalone lazy-loaded de la feature auth para solicitar el enlace y definir la nueva contraseña con el token de la URL, consumiendo los endpoints forgot y reset. Sin login automático: tras el éxito se redirige al login.

## Entregables

- src/app/features/auth/forgot-password/forgot-password.component (formulario reactivo con correo requerido y con formato válido, PrimeNG + Tailwind; muestra siempre el mensaje genérico 'si el correo existe, recibirás instrucciones'; manejo del 429 con mensaje claro)
- src/app/features/auth/reset-password/reset-password.component (lee token de la query, campos nueva contraseña y confirmación con validación de coincidencia, muestra errores del backend de política; ante token caducado/usado muestra mensaje y enlace para solicitar uno nuevo; al éxito redirige a /login con aviso)
- Métodos forgotPassword() y resetPassword() en core/auth.service contra /api/v1/auth/password/forgot y /reset
- Rutas públicas lazy en app.routes.ts (forgot-password, reset-password) y enlace '¿Olvidaste tu contraseña?' en la pantalla de login
- Pruebas Jest: forgot-password.component.spec (correo inválido/vacío no envía, mensaje genérico, 429), reset-password.component.spec (confirmación distinta, política rechazada, token inválido, éxito y redirección) y auth.service.spec para los dos métodos nuevos
- Actualizar frontend/README.md si cambian rutas o scripts de prueba

## Observaciones de la revisión

- **mayor** (buenas_practicas) `frontend/src/app/features/auth/forgot-password/forgot-password.component.ts:41`: `Validators.email({ value } as AbstractControl)` castea un objeto parcial a AbstractControl; funciona en runtime pero es frágil, y además el validador de Angular ya queda redundante con la regex. Adicionalmente `trimmedEmail` está duplicado con el del login (mismo helper en login.component.ts), violando DRY y arriesgando divergencia en las reglas de correo.
- **mayor** (criterio_aceptacion) `frontend/src/app/features/auth/reset-password/reset-password.component.ts:160`: handleError solo trata 410 como token inválido; 400 se trata como error de política. Si el backend responde 400 por token inválido/malformado (o 404), el usuario ve un mensaje genérico de política sin el enlace para solicitar uno nuevo, incumpliendo TC-005/TC-006. Además el mapeo 410 depende de un contrato asumido que no se verifica en el diff.
- **menor** (pruebas) `frontend/src/app/features/auth/login/login.component.spec.ts:1`: Las pruebas existentes del login usan provideRouter([]) sin ActivatedRoute mockeado; LoginComponent ahora inyecta ActivatedRoute (funciona con provideRouter), pero el caso `?reset=ok` reemplaza el ActivatedRoute por un objeto parcial. Correcto, aunque el resetTestingModule dentro del test es frágil.
- **menor** (pruebas) `frontend/src/app/features/auth/forgot-password/forgot-password.component.spec.ts:54`: La prueba 'el mensaje es el mismo para cualquier correo válido' reinicia el TestBed y compara dos renders con el mismo mock, por lo que no verifica realmente nada sobre el backend y es redundante con la anterior.
