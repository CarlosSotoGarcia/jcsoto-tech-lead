# PT-01 — Entorno de desarrollo dockerizado (compose, Dockerfiles dev, .env.example, README raíz)

_BASE: Esqueleto del aplicativo_

Deja el entorno de desarrollo levantable con docker compose up: servicios backend (Spring Boot con código montado y recarga en caliente), frontend (Angular dev server con hot reload) y PostgreSQL, más un servidor SMTP de desarrollo (p. ej. MailHog) para el correo de recuperación. Incluye Dockerfiles de desarrollo (nombrados Dockerfile.dev en backend/ y frontend/, distintos del Dockerfile de producción), .env.example con las variables de la arquitectura (DB_*, JWT_*, IDLE_TIMEOUT_MINUTES, MAIL_*, FRONTEND_BASE_URL, CORS_ALLOWED_ORIGINS, API_BASE_URL) y README.md raíz con requisitos previos, cómo levantar, puertos y URLs (incluida Swagger), variables de entorno, cómo correr pruebas dentro de los contenedores, cómo detener/limpiar y enlaces a los README de backend y frontend.

## Entregables

- docker-compose.yml de desarrollo en la raíz (backend, frontend, postgres, mailhog)
- backend/Dockerfile.dev y frontend/Dockerfile.dev con volumen y recarga en caliente
- Healthcheck de postgres y depends_on
- Archivo .env.example
- README.md raíz con guía de despliegue en desarrollo y enlaces a los README de servicios
- .gitignore y .dockerignore

## Se da por terminado cuando

- Compila, corre y pasa sus pruebas.

## Observaciones de la revisión

- **mayor** (criterio_aceptacion) `backend/Dockerfile.dev:10`: La recarga en caliente del backend no está garantizada: `mvn spring-boot:run` con devtools solo reinicia cuando cambian las clases compiladas en target/classes, y nada recompila al editar el código fuente montado. Además el CMD activa el perfil `dev` (-Dspring-boot.run.profiles=dev) y compose también fija SPRING_PROFILES_ACTIVE=dev, pero la arquitectura solo define application.yml y application-prod.yml; no hay application-dev.yml (redundante y confuso). El PR reconoce que depende de que el pom incluya devtools, sin acordarlo en ningún paquete.
- **mayor** (buenas_practicas) `docker-compose.yml:37`: La dependencia del backend en `mailhog` y `PORT: 8080` es correcta, pero el backend no tiene healthcheck y el frontend solo usa `depends_on: [backend]` sin condición; además `docker-compose.yml` y el `.dockerignore` raíz excluyen `*.md`/compose, lo que no afecta al build porque los contextos son ./backend y ./frontend (el .dockerignore raíz es inútil). Los contextos de build tienen sus propios .dockerignore.
- **mayor** (buenas_practicas) `frontend/Dockerfile.dev:10`: El CMD ejecuta `npm ci || npm install` en cada arranque del contenedor sobre un volumen anónimo/nombrado de node_modules montado bajo el bind mount ./frontend:/app. `npm ci` borra node_modules antes de instalar y se repite en cada `up`, lo que hace lento el arranque; además, si falla `npm ci` (lockfile ausente) cae a `npm install` silenciosamente. Además `CHOKIDAR_USEPOLLING` es redundante con `--poll 2000`.
- **menor** (seguridad) `.env.example:13`: Los valores de ejemplo de JWT_SECRET y DB_PASSWORD son válidos y funcionales (cumplen la longitud mínima), así que un usuario que copie el archivo sin cambiarlos levanta con secretos conocidos. Además Postgres (5432) queda publicado en el host en todas las interfaces.
- **menor** (buenas_practicas) `docker-compose.yml:56`: `API_BASE_URL` se pasa al contenedor del frontend como variable de entorno, pero `ng serve` no la lee en runtime; la arquitectura la inyecta en nginx/config.json solo en producción. En dev no tendrá efecto salvo que el esqueleto del frontend lo implemente.
- **menor** (criterio_aceptacion) `README.md:83`: El criterio "compila, corre y pasa sus pruebas" no se puede verificar: `docker compose up` no funciona hasta que existan backend/pom.xml y frontend/package.json (lo admite el README). Los comandos de prueba del README (`mvn test`, `npm test`, `npm run lint`) asumen scripts que aún no existen. Tampoco están enlazados README de backend/frontend que aún no existen (enlaces rotos).
