# PT-05 — Despliegue: Dockerfiles de producción y CI con GitHub Actions

_BASE: Esqueleto del aplicativo_

Deja el aplicativo desplegable en Cloud Run: backend/Dockerfile multi-stage (maven:3.9-eclipse-temurin-21 y eclipse-temurin:21-jre, puerto 8080, healthcheck /actuator/health) y frontend/Dockerfile multi-stage (node:20-alpine y nginx:alpine, fallback a index.html, /healthz, API_BASE_URL inyectada en runtime vía nginx.conf.template). Workflows de GitHub Actions: en PR, mvn verify en backend y npm ci, lint y jest en frontend; en push a main, docker build, push a Artifact Registry y gcloud run deploy por servicio con Workload Identity Federation, reconstruyendo cada servicio solo si cambian sus rutas. Actualiza el README raíz con la sección de despliegue.

## Entregables

- backend/Dockerfile de producción
- frontend/Dockerfile de producción y nginx.conf.template con /healthz
- Workflow CI de PR (backend y frontend con filtros por ruta)
- Workflow de deploy en push a main con Artifact Registry, Cloud Run y WIF
- Documentación de variables y secretos de despliegue en el README raíz

## Observaciones de la revisión

- **mayor** (criterio_aceptacion) `frontend/Dockerfile:8`: La arquitectura y el paquete exigen `npm ci`, pero el Dockerfile (y ci.yml línea ~62) hacen fallback a `npm install` cuando no existe package-lock.json. Los archivos del repo no listan package-lock.json, así que el build y el CI de producción no son reproducibles y no cumplen 'npm ci' en el frontend.
- **mayor** (criterio_aceptacion) `backend/Dockerfile:33`: El HEALTHCHECK depende de /actuator/health, pero en el diff no se ve que spring-boot-starter-actuator esté en el pom ni que SecurityConfig permita /actuator/health sin autenticación (hay un ActuatorHealthTest en el repo, pero no se puede confirmar aquí). Además `server.port=${PORT}` se asume en application-prod.yml sin verificarse en este PR. Si falta algo, el contenedor queda unhealthy.
- **mayor** (buenas_practicas) `.github/workflows/deploy.yml:74`: `--set-env-vars` interpola `${{ vars.* }}` directamente dentro del script de shell (inyección de expresiones/comillas si algún valor contiene `$`, comillas o `@`, p. ej. DB_URL con `&` y `?`, lo que además rompe la línea de shell sin comillas internas). Además usa el delimitador `^@^` pero DB_URL o CORS podrían contener `@`.
- **mayor** (arquitectura) `.github/workflows/deploy.yml:8`: El despliegue en push a main no depende de que el CI pase (mvn verify/jest) y el backend se construye con `-DskipTests` en el Dockerfile. Se puede desplegar código roto a producción.
- **menor** (arquitectura) `.github/workflows/deploy.yml`: Las variables de entorno de la arquitectura incluyen SPRING_PROFILES_ACTIVE, etc., y todo se pasa por `vars` de GitHub, incluido DB_URL/DB_USER y --allow-unauthenticated para el backend; no hay restricción de swagger en prod verificable. Además el frontend pasa API_BASE_URL sin comillas de protección.
- **menor** (buenas_practicas) `.github/workflows/ci.yml`: El filtro por rutas hace que un PR que solo toca la raíz (p. ej. README, docker-compose) no ejecute ningún job; si los jobs son checks requeridos, el PR quedaría bloqueado esperando. Además `dorny/paths-filter` necesita `pull-requests: read`, que sí está, pero el job `changes` hace checkout innecesario en PR.
- **menor** (buenas_practicas) `frontend/nginx.conf.template:22`: `/config.js` se genera con `${API_BASE_URL}` sin escapar: un valor con comillas o barras invertidas rompería el JS. Además la imagen nginx:alpine solo aplica envsubst a variables definidas en el entorno; `ENV API_BASE_URL=""` cubre el caso vacío. Los `add_header` dentro de location anulan los del nivel superior (no hay), sin problema, pero `gzip_types` no incluye text/html por defecto (sí lo comprime).
- **menor** (pruebas): El paquete no agrega pruebas y las imágenes/workflows no se ejecutaron ('Compila, corre y pasa sus pruebas' no se puede confirmar). No hay verificación automática del build de Docker en PR.
- **menor** (buenas_practicas) `backend/Dockerfile:16`: Se instala curl en la imagen final solo para el healthcheck, aumentando superficie de ataque; Cloud Run además ignora HEALTHCHECK de Docker.
