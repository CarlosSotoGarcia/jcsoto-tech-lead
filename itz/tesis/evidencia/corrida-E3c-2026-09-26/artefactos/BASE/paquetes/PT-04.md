# PT-04 — Shell del frontend React + MUI

_BASE: Esqueleto del aplicativo_

Scaffolding de apps/frontend: Vite + React + TypeScript, theme de MUI, router con layouts y rutas placeholder, TanStack Query, cliente HTTP con refresh automático, AuthContext y guards de ruta vacíos de reglas de negocio, generación de tipos desde OpenAPI y setup de pruebas. También crea el README del frontend.

## Entregables

- Proyecto Vite + React + TS con scripts: dev, build, preview, test, lint, typecheck y gen:api (openapi-typescript desde /api/docs-json hacia src/api/schema.d.ts)
- src/app/: theme.ts (theme MUI central), queryClient.ts, providers.tsx (ThemeProvider, CssBaseline, QueryClientProvider, AuthProvider) y router.tsx con layout público y layout autenticado
- Rutas placeholder: /login, /registro, /verificar-correo, /olvide-contrasena, /restablecer, /mis-vehiculos y /interno, además de una página 404
- src/api/http.ts: wrapper de fetch con VITE_API_BASE_URL, credentials include, header Authorization desde memoria, reintento único tras un 401 vía /auth/refresh y parseo de ErrorDto
- src/auth/: AuthContext (access token en memoria, sin flujos de negocio), RequireAuth, RequireRole y rutaInicialPorRol.ts
- src/shared/: mapa único de códigos de error a mensajes (vacío o extensible) y carpeta validation/
- Vitest + Testing Library + MSW configurados en src/test/, con una prueba del router y otra del reintento del cliente HTTP
- apps/frontend/README.md: qué hace, cómo levantarlo solo y con compose, variables de entorno (VITE_API_BASE_URL), cómo generar los tipos de la API, cómo correr las pruebas y la estructura de carpetas
- Actualización del README de la raíz con el comando gen:api

## Observaciones de la revisión

- **mayor** (criterio_aceptacion) `apps/frontend/package.json:21`: Se agregan dependencias nuevas (@tanstack/react-query, react-router-dom, msw, openapi-typescript), pero el diff no incluye la actualización del package-lock.json del workspace. La arquitectura indica que la CI y los Dockerfile usan `npm ci`, que falla cuando package.json y el lockfile no coinciden. Eso impediría cumplir «compila, corre y pasa sus pruebas».
- **menor** (buenas_practicas) `apps/frontend/src/api/http.ts:168`: Una petición enviada con el token viejo puede recibir su 401 cuando otro refresh concurrente ya terminó (refreshEnCurso vuelve a null). En ese caso dispara un segundo POST /auth/refresh innecesario, que rota otra vez el refresh token. El caso de prueba concurrente solo cubre los 401 que llegan mientras el refresh sigue en curso.
- **menor** (buenas_practicas) `apps/frontend/src/auth/AuthContext.tsx:62`: Cuando el cliente HTTP limpia el token (refresh fallido), el estado pasa a anónimo, pero `usuario` sigue en el state y la caché de TanStack Query conserva los datos del usuario anterior. Si luego alguien vuelve a poner un token en el store, el usuario anterior 'reaparece'. Además, la arquitectura pide limpiar la caché de Query al cerrar la sesión.
