# PT-05 — Dockerfiles de producción y CI/CD a Cloud Run

_BASE: Esqueleto del aplicativo_

Deja el aplicativo desplegable: Dockerfiles de producción multi-stage para los dos servicios de Cloud Run, nginx.conf del frontend y los workflows de GitHub Actions para PR y para el despliegue desde main.

## Entregables

- apps/backend/Dockerfile (producción): build node:20-alpine (npm ci, prisma generate, nest build) y runtime node:20-alpine con dependencias de producción, dist y prisma; usuario no root; PORT=8080; CMD npx prisma migrate deploy && node dist/main.js
- apps/frontend/Dockerfile (producción): build node:20-alpine (npm ci, vite build con ARG VITE_API_BASE_URL) y runtime nginx:1.27-alpine sirviendo dist en $PORT=8080
- apps/frontend/nginx.conf: fallback SPA, GET /healthz y escucha en $PORT mediante una plantilla envsubst
- Archivo .github/workflows/ci.yml en cada PR, con filtros por app afectada: lint, typecheck, Jest con un servicio postgres para los e2e, prisma validate, Vitest y build de las dos imágenes Docker de producción
- Archivo .github/workflows/deploy.yml en main: autenticación con Workload Identity Federation, build y push a Artifact Registry con el tag del SHA y gcloud run deploy de itz-agenda-api (Cloud SQL, secretos de Secret Manager, probes a /api/health) y de itz-agenda-web (probe a /healthz)
- docs/despliegue.md o una sección en el README de la raíz con las variables, secretos y recursos GCP necesarios (Cloud SQL, Secret Manager, Artifact Registry, Load Balancer /api → backend)

## Se da por terminado cuando

- Compila, corre y pasa sus pruebas.

## Observaciones de la revisión

- **menor** (criterio_aceptacion) `.github/workflows/ci.yml:122`: El criterio de terminado es «compila, corre y pasa sus pruebas», pero el CI solo construye las imágenes y nunca las ejecuta. Si nginx.conf tiene un error, el envsubst de ${PORT} falla o la API no arranca como usuario node, la CI no lo detecta y el problema aparecería recién en el primer despliegue.
- **menor** (buenas_practicas) `.github/workflows/deploy.yml:13`: El deploy se dispara con cualquier push a main sin comprobar que la CI haya pasado para ese commit. La única protección es la regla de rama que recomienda la documentación, así que un push directo o un merge que se salte los checks despliega a producción sin pruebas.
- **menor** (buenas_practicas) `.github/workflows/deploy.yml:89`: Las variables no definidas en GitHub llegan a Cloud Run como cadenas vacías (SMTP_PORT, SMTP_HOST, MAIL_FROM, etc.). El comentario dice que la API las trata como no definidas, pero env.schema.ts no forma parte del diff. Si el esquema usa, por ejemplo, `z.coerce.number()`, un SMTP_PORT vacío se convierte en 0 y la API no arrancaría.
- **menor** (buenas_practicas) `apps/backend/Dockerfile:27`: Los Dockerfiles y el CI usan `npm install` como alternativa cuando no existe package-lock.json. Así los builds de producción no son reproducibles y pueden desplegar versiones de dependencias distintas de las que se probaron. Además, `cache: npm` de setup-node supone que existe un lockfile.
- **menor** (seguridad) `.github/workflows/deploy.yml:48`: Las acciones de terceros (dorny/paths-filter, docker/*, google-github-actions/*) se referencian por tag mutable. El workflow de deploy tiene `id-token: write` y acceso a producción, así que una acción comprometida podría hacerse pasar por la cuenta de servicio de despliegue.
- **menor** (buenas_practicas) `apps/frontend/nginx.conf:35`: El comentario promete caché «larga e inmutable» para /assets/, pero `expires 1y` solo genera `Cache-Control: max-age`, sin `immutable`.
