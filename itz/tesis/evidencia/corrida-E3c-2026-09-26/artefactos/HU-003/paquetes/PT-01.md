# PT-01 — Backend: solicitud de enlace de restablecimiento (POST /auth/password/solicitar)

_HU-003: Recuperación de contraseña mediante enlace enviado por correo_

Crea el módulo password-recovery con el endpoint de solicitud. Siempre responde 202 con el mismo cuerpo neutro, exista o no el correo. Si el usuario existe, emite un TokenUnUso RESTABLECER_PASSWORD: aleatorio con crypto.randomBytes, guardado como hash SHA-256 y con expiración de RESET_TTL_MINUTOS=60. El correo con el enlace HTTPS ${FRONTEND_URL}/restablecer?token= se envía de forma asíncrona para que el tiempo de respuesta no dependa de si el correo existe. Si el correo no existe, no se envía nada. Aplica límite de frecuencia por IP y por correo normalizado con @nestjs/throttler, sin cambiar la respuesta visible. Valida el formato del correo con class-validator y responde 400 con ErrorDto. Audita RESET_SOLICITADO con usuario (si existe), IP y user-agent, sin datos sensibles. Supuesto abierto que confirma el PO: no se define si una nueva solicitud invalida los enlaces anteriores que siguen vigentes. Este paquete no lo decide y lo deja documentado como pendiente.

## Observaciones de la revisión

- **mayor** (seguridad) `apps/backend/src/modules/password-recovery/password-recovery.service.ts:71`: Todos los eventos RESET_SOLICITADO guardan `metadata.correo` con el correo normalizado en claro, también cuando el correo no está registrado o se superó un límite. Así, la auditoría append-only acumula cualquier correo que alguien teclee, sea de un tercero o de una lista de enumeración. Es un dato personal, y la HU y la arquitectura piden auditar 'usuario (si existe) e IP, sin guardar datos sensibles'. Además choca con el propio LimitadorFrecuencia, que hashea el correo precisamente 'para no dejar correos legibles'. Las pruebas unitarias (y la limpieza del e2e) fijan este comportamiento.
- **menor** (pruebas) `apps/backend/src/modules/password-recovery/password-recovery.service.spec.ts:271`: En la prueba 'termina igual que con un correo registrado', la variable `conCuenta` guarda el resultado del caso SIN cuenta (el beforeAll simula buscarPorCorreoNormalizado → null) y `registrado` el del caso con cuenta. Los nombres están invertidos y confunden al leerla.
- **menor** (pruebas) `apps/backend/test/password-recovery-solicitar.e2e-spec.ts:322`: La prueba de tiempos (TC-010) compara medianas de 20 muestras contra una base de datos real en CI. El camino con cuenta hace un INSERT más (el token) y construye el enlace, así que en runners cargados la prueba puede fallar de forma intermitente.
